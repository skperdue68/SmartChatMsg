Start here

SmartChatMsg prepares reusable announcements in ESO chat. You press Enter to send. It can prepare messages on demand, at startup, on zone arrival, or during scheduled promotion periods. It runs only while ESO is open and the addon is loaded; it cannot post while you are offline.

Version 3.0 targets ESO API 101051. Required libraries: LibAddonMenu-2.0 version 34 or newer and LibAddonMenuDatePicker. Sliders are included in LibAddonMenu; no separate slider library is required. LibDebugLogger is optional.

Install, update, and back up

Extract the SmartChatMsg folder into your ESO live/AddOns directory and enable the addon and required libraries. Keep a backup of your current live/SavedVariables/SmartChatMsg.lua before replacing or editing it. Do not overwrite SavedVariables while ESO is running: the game can replace your changes when it exits.

Open /scm for settings. If you are starting fresh, create a command, select its guild, choose an output channel, and add at least one message. One command can have different messages and settings for different guilds. Existing older schedule formats are not supported by this release; ordinary message content should be backed up before updating. The applications do not automatically convert old schedules.

Optional companion: SmartChatMsg-Web

For a larger editor and visual planning tools, visit scm.perdues.me. Install SmartChatMsg and run ESO with the addon enabled at least once, then exit ESO fully so it writes live/SavedVariables/SmartChatMsg.lua. Open that file in the companion app; it supplies your account and saved guild/configuration information.

The web companion provides period editing, message libraries, previews, a schedule overview, and a draggable day view. You can also configure schedules directly in ESO. Download the updated Lua file, keep a backup, and install it as SmartChatMsg.lua in SavedVariables while ESO is closed. A browser download does not itself update your ESO installation. The addon still handles live chat detection and message preparation.

When using the optional shared server library, saved configurations are public to its users. Loading a library copy opens it for editing; downloading includes your subsequently applied changes. Review the target account and guild before installing.

Commands, guilds, channels, and message pools

Create a short command name such as recruit or tours. Under Create / Edit / Delete Messages, select the command and guild, then choose Guild, Officer, Zone, or Group. Group chat uses /g; Guild and Officer chat use the selected guild's current slot. The guild remains the configuration identity even when output goes to Zone or Group.

Enter a message and click Add. Update and Delete edit existing messages. Add several alternatives for a varied pool: selection is randomized with usage weighting. Keep the final expanded announcement under 350 characters; substitutions can make the output longer than its template. Use Test to view parsed output in your own chat without posting it.

For On Demand and Startup, only enabled messages are eligible for selection. Disabling one removes it from your outgoing pool without deleting its content; incoming duplicate monitoring is separate. For Scheduled, choose eligible messages separately for each period. A period needs at least one suitable message to deliver an announcement.

Global settings and timezones

Default guild is used by ordinary slash commands when you omit a guild argument. Auto-Remove Pending Chat After uses a slider from 30 to 300 seconds, with exact seconds entry. It is the timeout for an unsent prepared message; player-edited chat is protected.

The default scheduling timezone can be ET, CT, MT, or PT. Each guild can override it under Scheduling > Guild timezone. US daylight-saving rules are calculated for the event date. Mountain follows DST-observing Mountain time. All scheduling dates and clocks use the effective guild scheduling timezone, independently of your computer timezone.

Changing the default timezone keeps the entered calendar dates and clock times for guilds using that default, changing their UTC moments. Explicit guild overrides stay in effect. Changing a guild timezone moves that guild's schedules to the same clock time in the selected zone. Literal timezone text in messages is not rewritten; prefer event substitutions.

The missing spring clock hour is invalid. Repeated autumn clock hours use the configured fold choice where available; avoid ambiguous hours when possible.

Run At: On Demand, Startup, or Scheduled

On Demand waits for your custom command, for example /recruit 1. The optional number identifies the guild slot; without it the configured default is used. It can prepare one message or engage timed repetition.

Startup engages ordinary delivery when the addon initializes, including UI reload. Its custom command remains available. This is useful for ordinary repeating or zone-arrival workflows.

Scheduled uses the event and Period Timeline instead. Save and activate engages it automatically when its times are eligible. You do not need to launch a custom command. A command used only by scheduled combinations does not register its own slash command; switching it to On Demand or Startup restores ordinary command use.

Ordinary delivery controls

Repeat Frequency: Off means no timed repeat; otherwise it controls the interval for ordinary repeated messages. The slider covers Off through 1440 minutes. Retry Delay: after an unsent repeated message times out, this controls when to try again. Off uses the normal repeat behavior. Its slider covers Off through 60 minutes, capped by the smaller positive Repeat Frequency and Cooldown. Retry is unavailable without timed repetition.

Auto Populate Chat on Zone prepares a message when you enter an eligible parent zone. This replaces ordinary timed repetition, so Repeat Frequency is disabled while it is enabled. Cooldown is the automatic zone cooldown; its slider covers 15–480 minutes. Existing values outside slider ranges are retained until deliberately changed. Exact-minute entry remains available.

Open Status Panel on Run shows the status window when this combination starts. Notify Sound selects the preparation sound; Preview plays it in ESO and None is silent. These settings belong to the selected command and guild.

Build an event and its Period Timeline

Set Run At to Scheduled and open Scheduling. Under Event date and time, select the actual event date and time. This is the event itself, not when advertising starts. Set Event duration if it continues after its start. Duration 0 displays Not set. Choose recurrence and any special pattern, then configure Period Timeline.

Add a period, give it a Period Label, and set Period Starts and Period Stops using calendars and hour/minute/AM-PM controls. Dates displayed are based on an event occurrence; the saved relationships follow recurring events. Set Repeat Frequency and check the message pool for that period. Use different periods to change frequency and wording without creating separate commands.

Period Status can enable, pause, or disable the period while keeping its content. Normal promotion begins on or before the event. Enable Allow promotion after event starts for underway invitations; this control requires a positive event duration. Delivery is capped by the event end unless the closing exception applies.

The web editor orders periods chronologically and flags overlapping ordinary windows; adjacent windows can meet at the same boundary. Preview Period Timeline in ESO and click message text to test it at a simulated time in the selected period. Save and activate commits and enables the schedule; Save disabled retains it without running.

Example: an 8 PM event lasting two hours

Set Event Start Time to 8 PM and duration to 120 minutes. Create an early-promotion period from the previous evening to 6 PM with a four-hour frequency. Create a final-promotion period from 6 PM to 8 PM with a 30-minute frequency and more urgent messages.

Add a Send once, time-sensitive notice at 8 PM: “We are starting!” Then create an underway period from 8 PM to 10 PM, enable Allow promotion after event starts, and select “come join us” messages. Keep the end at 10 PM so invitations stop when the activity is over.

Use separate message selections for these periods. A starting notice should not share wording intended for several days before the event.

Send once, time-sensitive notices, and closing announcements

Send once means one confirmed announcement for that period and event occurrence. It does not repeat when its frequency comes around. A matching announcement from someone else can also complete it. Preparing chat alone does not complete it. A future event occurrence starts fresh.

Lateness allowance defines the short opportunity after a one-time notice becomes due. If the window passes while you are offline, the expired notice is skipped. Keep entire reminder window available until sent allows that one announcement during its full configured window instead of only the short grace.

Time-sensitive notices can bypass ordinary inter-schedule pacing, but still respect startup protection, chat safety, eligibility, duplicate suppression, and daily limits. They prepare chat; they do not automatically press Enter.

Allow a closing announcement after the event ends is an advanced exception for notices such as “The auction is closed.” It permits the selected period beyond the duration cap. Keep its own stop/grace short and usually enable Send once. It is different from ordinary invitations while an event is still running.

Availability and daily announcement limits

Availability restricts announcement weekdays and server-clock hours inside a period. These are advertising days, not the event's recurrence weekdays. An overnight window belongs to its opening date. Weekday and exact-date hour overrides can change particular windows; exact-date overrides take priority, and Reset removes the selected override.

Daily announcement limit is outside Availability and works even when hour restrictions are off. Slider 0 displays Unlimited; the slider goes through 20. Unchecked Share Limit to ALL periods means a separate daily maximum for this period. Checked shares one maximum across every period for the same command and guild. All selected messages count toward the same applicable limit; it is not a limit per template.

Confirmed sends and recognized matching announcements from other players count. Preparing, timing out, and retrying do not consume a send. Counts persist through reload/logout and reset at midnight in the scheduling timezone. Switching scope does not intentionally reset today's history. Status distinguishes Period daily limit reached from Command daily limit reached and shows the count/maximum.

/scm resetcooldowns also clears daily usage. Use it for testing, not to preserve a daily cap. Portable configuration exports do not copy another player's usage counters; recipient usage is retained where records match.

Recurrence and special patterns

Choose once, daily, weekly, every other week, monthly on date, or monthly on weekday. The original event date anchors the repeat pattern; the next occurrence is calculated automatically. Recurrence interval multiplies that unit. For the last Sunday of every month, use monthly on weekday, Last, Sunday.

Repeat on weekdays selects actual event occurrence days. It does not prevent advertising on other days: use Availability for advertising restrictions. Leave optional weekday overrides unset to follow the event date's weekday.

Last event of month selects the final occurrence of the recurring pattern in that calendar month. Messages can use Regular, Month-final, or All events groups. If no month-final alternatives are configured, regular messages provide the fallback.

Faction rotation uses an ordered selection of factions and a number of weeks per faction. The event itself can still run weekly. AD means Aldmeri Dominion, EP means Ebonheart Pact, and DC means Daggerfall Covenant. Use %eventfaction% to insert the selected faction's full name.

Rotating event uses an ordered list of named activities and a number of occurrences per activity. Use %eventactivity% for the selected activity. Event Date anchors the first entry. Cancellation can Keep rotation (consume its place) or Postpone rotation (hold its place); undoing the cancellation recalculates later selections. Exceptions are stored with the schedule, so ESO does not need a remote database.

Important times and message substitutions

Important times names a moment such as gathering or ticket sales close. Add one, choose its date and time in the scheduling timezone, and use the substitution key displayed in settings. The editor stores its offset from the event, so it follows recurring events. Example: an 8 PM event with a 7 PM tickets deadline stores one hour before the event.

General tokens: %timeofday% (morning, afternoon, or evening), %guild% (resolved guild), and %zone% (current zone). Older greeting aliases remain recognized, but only one general time-of-day choice is needed in an insert menu. Tokens are case-insensitive.

Scheduled tokens: %eventwhen% gives a human-readable day reference; %eventdate% gives the event date; %eventtime% gives its clock time with timezone; %eventcountdown% gives time remaining. %eventfaction% and %eventactivity% use the corresponding special pattern.

Adjustable offsets include %eventwhen-1h%, %eventdate-1h%, %eventtime-1h%, and %eventcountdown-1h%. You can use other supported offsets such as -2h or -1d. Named moments use %eventwhen:tickets%, %eventdate:tickets%, %eventtime:tickets%, and %eventcountdown:tickets%, where tickets is the displayed key. Test before using them; a deadline already in the past should not be advertised as still open.

Example template: “Family business: raffle %eventwhen% at %eventtime% (%eventcountdown%). Tickets close %eventwhen-1h% at %eventtime-1h% (%eventcountdown-1h%).” Use a different period after ticket sales close so it no longer invites purchases.

Ordinary commands have no scheduled event context. Use general tokens there. Recognized literal date/time text can receive a calculated countdown; it does not create an event schedule. Preview the final message to check its meaning and expanded length.

Duplicate detection, cooldowns, and chat safety

Other players' matching announcements update your command/guild cooldowns even when you have not engaged that command. Guild and Officer matches require the correct guild and channel; Zone requires Zone and Group requires Group. Your own incoming messages are excluded from peer detection.

Matching understands supported substitutions and generated countdown differences, so changing remaining time does not prevent a match. Fixed text is normalized, with conservative spelling tolerance for sufficiently long messages. This is not unrestricted semantic matching: numbers, guild identities and other protected content are not casually ignored. A recognized peer announcement adds the existing randomized 30–90 seconds to help separate clients.

Scheduled automation waits three minutes after startup. An ordinary scheduled send pauses other scheduled commands for five minutes; the same command can use a shorter configured interval. Multiple eligible schedules are randomized. Time-sensitive notices have the pacing exception described above.

A busy chat draft is protected. SmartChatMsg prepares an announcement only when eligible and safe; sounds and local notifications help you notice it. Start, end, period-change and skip messages explain schedule activity. Cooldown/status changes can come from another player's announcement, not only your own sends.

Status window, testing, and recovery commands

/scm opens settings. /scm schedule opens scheduling. /scm status toggles the status panel. /scm retry restores the latest eligible unsent message from the current UI session, including a pending message still protected by its timeout watcher. You do not have to wait for timeout. Player-edited drafts must be cleared first; normal eligibility and peer cooldown rules remain in effect. /scm resetcooldowns clears stored cooldown/testing history, including daily counts. /scmdebug on and /scmdebug off control debugging.

/scm send <name> [guild number] requests an extra scheduled message, for example /scm send tours 1. It uses the currently eligible period/pool and normal substitutions. Eligibility, safety, peer suppression and applicable limits still apply; it does not enable a disabled schedule or make an expired period active. Only a confirmed send records a send.

The status panel groups Auto and Repeat Commands, with collapsible sections. Cards identify Scheduled or On Demand, show activity/state, promotion range, selected period/frequency and sending information. Enable/Disable affects that card's command and guild. Active cards sort first, so disabling may move a card. Next Send is shown only for active entries; a due timestamp includes a countdown and clock time with seconds when applicable.

To test safely, create a short event a few minutes ahead, use a small message pool, and preview each period. Remember the startup delay, any existing daily limit and peer cooldown. Do not expect chat to be posted without Enter. If nothing prepares, inspect status for no eligible messages, a future window, protected chat, startup delay, spacing or a reached limit.

Import, export, and saved files

Use Import / Export Settings for portable configuration. Guild references are exported by name and resolved to the receiving player's current guild slots. Missing guild records are skipped with a local explanation. Matching command names are reconciled even if IDs differ. Review the import result before enabling automation.

Configuration includes command/guild delivery settings, messages, schedules, periods, important times, recurrence, rotations and exceptions, availability, and daily-limit scope. Portable transfers preserve recipient cooldown/usage history rather than adopting another player's runtime counters. Full SavedVariables files contain account-specific data; choose the correct account when editing them in the web companion.

The Lock button is not exposed in the ESO editor. Existing personal/locked metadata is still respected by transfer code; do not assume a full Lua backup or public server-library file hides private content. Keep backups before any replacement.

Message names and display order created by the companion are retained in saved data. ESO's settings have a different presentation and do not provide all of the companion's visual editing conveniences.
